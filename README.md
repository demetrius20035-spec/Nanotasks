# Nanotasks

**Оркестратор разработки на нано-задачах.** Большая модель-архитектор планирует,
маленькие локальные модели исполняют — по одной крошечной задаче за раз.

## Идея

Локальные модели (7B/14B/30B) хорошо пишут код, но «теряются» при работе с
инструментами: маленькому окну контекста (16K) не хватает места, чтобы держать в
голове весь проект. Nanotasks обходит это так: **всё состояние живёт в базе, а не
в контексте модели**. Маленькая модель становится почти чистой функцией
`промпт → артефакт` — ей не нужно помнить ничего, кроме одной задачи.

Три роли моделей:

| Роль | Где | Что делает |
|------|-----|-----------|
| **Архитектор** | большая, внешняя (QWEN/DeepSeek/Алиса/ГигаЧат) | ТЗ → ФС → TODO в формате, готовом к импорту |
| **Постановщик** (`prompt_builder`) | локальная (напр. Gemma) | из пункта TODO делает точный нано-промпт |
| **Кодер** (`coder`) | локальная (напр. QWEN Coder 14B) | из нано-промпта делает код |

```
ТЗ + ФС + TODO            ← архитектор (вне оркестратора, импорт вручную)
        │  импорт (YAML)
        ▼
  ┌─────────────┐   для каждого пункта:
  │   База      │   ┌────────────────────────────────────────────────┐
  │  (DuckDB)   │──▶│ собрать контекст зависимостей                   │
  │  проект/    │   │   → постановщик делает нано-промпт              │
  │  пункты/    │   │   → кодер делает код                            │
  │  промпты/   │◀──│   → артефакт в базу → ревью человеком           │
  │  артефакты  │   └────────────────────────────────────────────────┘
  └─────────────┘
        │  сборка
        ▼
  дерево файлов проекта (output/)
```

### Сердце системы — сборка контекста

Кодер работает без памяти. Чтобы он не выдумывал сигнатуры, перед генерацией
оркестратор собирает **контракты зависимостей** пункта (поле `depends_on`):
путь файла + уже сгенерированный код зависимостей — и подмешивает их в промпт.
Без этого независимо сгенерированные файлы не склеятся. См.
[`nanotasks/pipeline/context.py`](nanotasks/pipeline/context.py).

## Установка

```bash
pip install -r requirements.txt          # ядро + GUI
# или только ядро (без десктоп-интерфейса):
pip install duckdb PyYAML httpx
```

Python 3.10+. СУБД — встроенная **DuckDB** (один файл, сервер не нужен), спрятана
за слоем доступа к данным, так что при желании меняется на другой движок.

## Конфигурация

```bash
cp config/config.example.yaml config/config.yaml
```

Укажи endpoint'ы локальных моделей. Ollama и LM Studio говорят по
OpenAI-совместимому протоколу:

```yaml
models:
  prompt_builder:
    provider: openai_compatible
    base_url: http://localhost:11434/v1   # Ollama
    model: gemma2:27b
  coder:
    provider: openai_compatible
    base_url: http://localhost:1234/v1    # LM Studio
    model: qwen2.5-coder:14b
```

Провайдеры `alice` (YandexGPT) и `gigachat` уже есть каркасами в
[`nanotasks/llm/`](nanotasks/llm/) — допиши по своим примерам интеграции.

## Быстрый старт

### CLI (без GUI)

```bash
python -m nanotasks import examples/todo.example.yaml   # TODO → проект в базе
python -m nanotasks projects                            # список проектов
python -m nanotasks run 1                               # прогон с ревью на каждом пункте
python -m nanotasks run 1 --auto                        # прогон без ревью
python -m nanotasks assemble 1                          # собрать дерево файлов
```

### GUI

```bash
python -m nanotasks gui
```

Слева дерево пунктов, справа нано-промпт и код с кнопками
**Одобрить / Перегенерировать / Пропустить**. Прогон идёт в фоновом потоке.

## Формат TODO

Иерархический YAML (пункт → подпункт → подподпункт), готовый к импорту в базу.
Полный пример — [`examples/todo.example.yaml`](examples/todo.example.yaml).

```yaml
project:
  name: "Todo CLI"
  language: python
tasks:
  - key: "1.1"
    title: "Класс Task"
    type: code                 # group | code | yaml | config | doc | test
    file: "todoapp/models.py"
    body: "Определи dataclass Task с полями id:int, title:str, done:bool=False…"
  - key: "2.1"
    title: "Хранилище"
    type: code
    file: "todoapp/storage.py"
    depends_on: ["1.1"]        # контракт 1.1 подмешается в промпт
    body: "Класс Storage(path) с методами load()/save() поверх Task…"
```

## Конечный автомат пункта

```
pending → prompt_ready → code_ready → approved → written
                              ↘ failed / blocked / skipped
```

`group`-узлы кода не генерируют (`skipped`). Лист считается готовым к сборке в
состояниях `approved`/`written`. Зависимости должны быть готовы — иначе `blocked`.

## Структура проекта

```
nanotasks/
  models.py            доменные dataclass'ы и статусы
  config.py            загрузка YAML-конфига
  importer.py          YAML TODO → база
  cli.py               командный интерфейс (полный цикл без GUI)
  db/                  слой доступа к данным (DuckDB за DAL)
  llm/                 адаптеры моделей: openai_compatible, alice, gigachat
  pipeline/            context · prompt_builder · coder · orchestrator · assembler
  ui/app.py            десктоп-GUI на PySide6
```

## Статус и что дальше

MVP: полный цикл **импорт → нано-промпт → код → сборка дерева файлов** с ревью
человеком, CLI и GUI. Ядро проверено сквозным тестом.

Дорожная карта (по мере необходимости):
- API-вызов архитектора прямо из оркестратора (сейчас TODO импортируется вручную);
- шаг проверки артефактов (компиляция/линт/тест) и авто-«ремонт»;
- веб-автоматизация бесплатных веб-версий моделей;
- экспорт/импорт проектов целиком, ветвление версий артефактов.

> Примечание: GUI требует системных библиотек Qt (libEGL и пр.). В «голых»
> headless-контейнерах без них PySide6 не запускается — это ограничение
> окружения, а не кода; ядро и CLI от этого не зависят.
